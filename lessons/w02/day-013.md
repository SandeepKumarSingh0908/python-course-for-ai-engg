## Section 1: collections.deque

A `deque` (double-ended queue, pronounced "deck") supports O(1) append and pop from **both** ends. A regular list has O(1) append/pop on the right but O(n) insert/pop on the left because all elements must shift.

```python
from collections import deque

# Create a deque
dq = deque([1, 2, 3, 4, 5])

# O(1) operations on both ends
dq.append(6)        # right end:  deque([1, 2, 3, 4, 5, 6])
dq.appendleft(0)    # left end:   deque([0, 1, 2, 3, 4, 5, 6])

dq.pop()             # 6 -- from right
dq.popleft()         # 0 -- from left
```

### Bounded Deque (maxlen)

A deque with `maxlen` automatically discards items from the opposite end when the limit is reached. This is perfect for sliding windows and recent-history buffers.

```python
# Keep only the last 5 loss values during training
recent_losses = deque(maxlen=5)

for epoch in range(10):
    loss = 1.0 / (epoch + 1)   # simulated loss
    recent_losses.append(loss)
    avg = sum(recent_losses) / len(recent_losses)
    print(f"Epoch {epoch}: loss={loss:.3f}, rolling_avg={avg:.3f}")
```

### Rotate

```python
dq = deque([1, 2, 3, 4, 5])
dq.rotate(2)     # rotate right by 2: deque([4, 5, 1, 2, 3])
dq.rotate(-1)    # rotate left by 1:  deque([5, 1, 2, 3, 4])
```

### When to Use deque vs list

| Operation | list | deque |
|---|---|---|
| Append right | O(1) amortised | O(1) |
| Pop right | O(1) | O(1) |
| Append left | O(n) | O(1) |
| Pop left | O(n) | O(1) |
| Index access `d[i]` | O(1) | O(n) |

Use `deque` when you need fast operations on both ends. Stick with `list` when you need frequent random access by index.

## Section 2: collections.OrderedDict

Since Python 3.7, regular `dict` preserves insertion order. So why does `OrderedDict` still exist?

```python
from collections import OrderedDict

# OrderedDict considers order in equality comparisons
od1 = OrderedDict([("a", 1), ("b", 2)])
od2 = OrderedDict([("b", 2), ("a", 1)])
print(od1 == od2)  # False -- different order

# Regular dicts do NOT consider order in equality
d1 = {"a": 1, "b": 2}
d2 = {"b": 2, "a": 1}
print(d1 == d2)    # True -- same keys and values
```

### move_to_end

`OrderedDict` has a `move_to_end()` method that regular dicts lack.

```python
od = OrderedDict([("a", 1), ("b", 2), ("c", 3)])
od.move_to_end("a")            # move to the end
print(list(od.keys()))          # ['b', 'c', 'a']

od.move_to_end("a", last=False) # move to the beginning
print(list(od.keys()))          # ['a', 'b', 'c']
```

### LRU Cache Pattern

`OrderedDict` is the classic building block for a Least Recently Used cache:

```python
class LRUCache:
    def __init__(self, capacity):
        self.cache = OrderedDict()
        self.capacity = capacity

    def get(self, key):
        if key in self.cache:
            self.cache.move_to_end(key)  # mark as recently used
            return self.cache[key]
        return None

    def put(self, key, value):
        if key in self.cache:
            self.cache.move_to_end(key)
        self.cache[key] = value
        if len(self.cache) > self.capacity:
            self.cache.popitem(last=False)  # evict oldest

cache = LRUCache(3)
cache.put("model_v1", {"acc": 0.91})
cache.put("model_v2", {"acc": 0.93})
cache.put("model_v3", {"acc": 0.90})
cache.get("model_v1")                    # moves v1 to end
cache.put("model_v4", {"acc": 0.95})     # evicts v2 (oldest)
print(list(cache.cache.keys()))           # ['model_v3', 'model_v1', 'model_v4']
```

## Section 3: collections.ChainMap

A `ChainMap` groups multiple dicts into a single view. Lookups search each dict in order until the key is found. This is ideal for layered configurations where user overrides take precedence over defaults.

```python
from collections import ChainMap

defaults = {"lr": 0.001, "batch_size": 32, "optimizer": "sgd", "epochs": 100}
user_config = {"lr": 0.0003, "optimizer": "adam"}
cli_args = {"epochs": 10}

# CLI args > user config > defaults
config = ChainMap(cli_args, user_config, defaults)

print(config["lr"])          # 0.0003  (from user_config)
print(config["epochs"])      # 10      (from cli_args)
print(config["batch_size"])  # 32      (from defaults)
print(config["optimizer"])   # adam     (from user_config)
```

### Mutations Apply Only to the First Map

```python
config["new_key"] = "value"     # added to cli_args (the first map)
print(cli_args)                  # {'epochs': 10, 'new_key': 'value'}
```

### Practical Use: Environment-Specific Settings

```python
import os
from collections import ChainMap

env_vars = {k.lower(): v for k, v in os.environ.items() if k.startswith("ML_")}
file_config = {"ml_lr": "0.001", "ml_batch_size": "32"}
hard_defaults = {"ml_lr": "0.01", "ml_batch_size": "64", "ml_epochs": "50"}

settings = ChainMap(env_vars, file_config, hard_defaults)
# Environment variables override file config, which overrides hard defaults
```

## Section 4: Choosing the Right Data Structure

Here is a decision guide and time-complexity comparison to keep in your back pocket.

### Quick Decision Tree

1. **Need key-value mapping?** --> `dict` (or `defaultdict`, `Counter`, `OrderedDict`)
2. **Need ordered, mutable sequence with random access?** --> `list`
3. **Need fast append/pop on both ends?** --> `deque`
4. **Need immutable record with named fields?** --> `NamedTuple`
5. **Need unique elements or fast membership test?** --> `set` (or `frozenset`)
6. **Need immutable sequence (dict key, return value)?** --> `tuple`

### Time Complexity Comparison

| Operation | list | deque | dict | set |
|---|---|---|---|---|
| Index `[i]` | O(1) | O(n) | -- | -- |
| Search (`in`) | O(n) | O(n) | O(1) avg | O(1) avg |
| Append right | O(1)* | O(1) | -- | -- |
| Append left | O(n) | O(1) | -- | -- |
| Insert middle | O(n) | O(n) | -- | -- |
| Delete by value | O(n) | O(n) | O(1) avg | O(1) avg |
| Pop right | O(1) | O(1) | -- | -- |
| Pop left | O(n) | O(1) | -- | -- |
| Get by key | -- | -- | O(1) avg | -- |
| Add element | -- | -- | O(1) avg | O(1) avg |

\* amortised

### Real-World Scenario: Feature Store

```python
from collections import defaultdict, deque

# Feature store: fast lookup by user ID (dict),
# with a rolling window of recent feature values (deque)
feature_store = defaultdict(lambda: deque(maxlen=10))

# Simulate streaming feature updates
import random
for _ in range(50):
    user_id = f"user_{random.randint(1, 5)}"
    feature_val = round(random.random(), 3)
    feature_store[user_id].append(feature_val)

# Latest features for user_1
print(f"user_1 recent features: {list(feature_store['user_1'])}")
# Efficiently get rolling average
vals = feature_store["user_1"]
print(f"user_1 rolling avg: {sum(vals) / len(vals):.3f}")
```

## Section 5: Worked Example -- Config System with ChainMap

```python
from collections import ChainMap

def load_defaults():
    return {
        "model": "bert-base",
        "lr": 0.00005,
        "batch_size": 16,
        "epochs": 3,
        "max_seq_length": 128,
        "warmup_steps": 100,
    }

def load_experiment_config():
    """Simulate loading from a YAML file."""
    return {
        "model": "bert-large",
        "lr": 0.00003,
        "batch_size": 8,
    }

def parse_cli_args():
    """Simulate CLI overrides."""
    return {
        "epochs": 5,
    }

# Build layered config
config = ChainMap(parse_cli_args(), load_experiment_config(), load_defaults())

print("Final configuration:")
for key in sorted(set().union(*config.maps)):
    print(f"  {key}: {config[key]}")

# Check where a specific value came from
for i, mapping in enumerate(config.maps):
    if "lr" in mapping:
        source = ["CLI", "experiment", "defaults"][i]
        print(f"\nlr={config['lr']} comes from: {source}")
        break
```

## Common Mistakes

- **Using a list as a queue:** `list.pop(0)` is O(n) because every element shifts. Use `deque.popleft()` instead.
- **Assuming `OrderedDict` is needed for order:** In Python 3.7+, regular `dict` is ordered. Only use `OrderedDict` if you need order-aware equality or `move_to_end()`.
- **Forgetting that `ChainMap` lookups stop at the first match:** If the same key exists in multiple maps, only the first one found is returned. This is the intended behaviour for config layering.
- **Over-engineering data structures:** For small collections (hundreds of items), the choice between list and set for lookups barely matters. Optimise only when scale demands it.
