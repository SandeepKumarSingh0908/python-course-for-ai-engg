# Day 16 - Inheritance & Polymorphism

**Module:** Week 3 -- OOP, Modules & Packages | **Time:** ~60 min (35 read + 25 lab)

> Every time you build a custom sklearn transformer, a PyTorch `nn.Module`, or a LangChain
> tool, you are subclassing an existing class. Inheritance is the mechanism that lets you
> reuse framework code while customizing only the parts you need. Polymorphism means your
> custom class slots into the framework just like any built-in one -- `pipeline.fit()` does
> not care whether your transformer is `StandardScaler` or `MyCustomScaler`.

## By the end of this lesson you will

- Use single and multiple inheritance with `super()` to reuse parent behavior
- Trace Python's Method Resolution Order (MRO) to predict which method runs
- Define abstract interfaces with `abc.ABC` and `@abstractmethod`
- Leverage duck typing and polymorphism to write flexible, framework-ready code

## Section 1: Single Inheritance and `super()`

### Basic subclassing

```python
class BaseModel:
    """Shared logic for all models."""

    def __init__(self, name: str):
        self.name = name
        self.is_fitted = False

    def fit(self, X, y):
        raise NotImplementedError("Subclasses must implement fit()")

    def summary(self) -> str:
        status = "fitted" if self.is_fitted else "unfitted"
        return f"{self.name} [{status}]"


class LinearModel(BaseModel):
    """Adds coefficients on top of BaseModel."""

    def __init__(self, name: str, regularization: float = 0.0):
        super().__init__(name)  # call BaseModel.__init__
        self.regularization = regularization
        self.coefficients: list[float] = []

    def fit(self, X: list[list[float]], y: list[float]):
        # Simplified: just store the number of features
        self.coefficients = [0.0] * len(X[0])
        self.is_fitted = True
        return self

    def summary(self) -> str:
        base = super().summary()  # reuse parent's summary
        return f"{base} | coefs={len(self.coefficients)} | reg={self.regularization}"


model = LinearModel("ridge", regularization=0.1)
model.fit([[1, 2], [3, 4]], [5, 6])
print(model.summary())
# ridge [fitted] | coefs=2 | reg=0.1
```

### Why `super()` and not `BaseModel.__init__(self, ...)`

`super()` is MRO-aware. It follows the correct chain in multiple inheritance scenarios.
Hard-coding the parent name breaks when you change the hierarchy.

## Section 2: Multiple Inheritance

Python supports inheriting from multiple classes. This is powerful but needs discipline.

```python
class Serializable:
    """Mixin: adds save/load capabilities."""

    def to_dict(self) -> dict:
        return {"class": type(self).__name__, "attrs": vars(self)}

    @classmethod
    def from_dict(cls, data: dict):
        obj = cls.__new__(cls)
        for k, v in data["attrs"].items():
            setattr(obj, k, v)
        return obj


class Loggable:
    """Mixin: adds logging."""

    def log(self, message: str):
        print(f"[{type(self).__name__}] {message}")


class SmartModel(BaseModel, Serializable, Loggable):
    """Inherits from BaseModel + two mixins."""

    def fit(self, X, y):
        self.log("Starting fit...")
        self.is_fitted = True
        self.log("Fit complete.")
        return self


m = SmartModel("smart-v1")
m.fit([], [])
print(m.to_dict())
# {'class': 'SmartModel', 'attrs': {'name': 'smart-v1', 'is_fitted': True}}
```

### Mixins

A mixin is a class designed to be combined with others via multiple inheritance. It adds
a small, focused capability (serialization, logging, caching) without being a standalone
entity. Convention: mixin classes don't define `__init__` or keep complex state.

## Section 3: Method Resolution Order (MRO)

When you call a method, Python searches classes in a specific order called the MRO
(C3 linearization).

```python
print(SmartModel.__mro__)
# (<class 'SmartModel'>, <class 'BaseModel'>, <class 'Serializable'>,
#  <class 'Loggable'>, <class 'object'>)
```

**Reading the MRO:** Python tries `SmartModel` first, then `BaseModel`, then
`Serializable`, then `Loggable`, and finally `object`. The first class that defines the
method wins.

```python
class A:
    def greet(self):
        return "A"

class B(A):
    def greet(self):
        return "B"

class C(A):
    def greet(self):
        return "C"

class D(B, C):
    pass

print(D.__mro__)
# D -> B -> C -> A -> object
print(D().greet())  # "B" -- B comes before C in the MRO
```

### Cooperative multiple inheritance with `super()`

```python
class A:
    def __init__(self):
        print("A.__init__")
        super().__init__()

class B(A):
    def __init__(self):
        print("B.__init__")
        super().__init__()

class C(A):
    def __init__(self):
        print("C.__init__")
        super().__init__()

class D(B, C):
    def __init__(self):
        print("D.__init__")
        super().__init__()

D()
# D.__init__
# B.__init__
# C.__init__
# A.__init__
```

Each `super()` call follows the MRO, so every class in the chain gets initialized exactly
once.

## Section 4: Abstract Base Classes

An abstract class defines an interface that subclasses must implement. You cannot
instantiate an abstract class directly.

```python
from abc import ABC, abstractmethod

class BaseTransformer(ABC):
    """Mimics sklearn's transformer interface."""

    @abstractmethod
    def fit(self, X: list[list[float]]) -> "BaseTransformer":
        """Learn parameters from data."""
        ...

    @abstractmethod
    def transform(self, X: list[list[float]]) -> list[list[float]]:
        """Apply the transformation."""
        ...

    def fit_transform(self, X: list[list[float]]) -> list[list[float]]:
        """Convenience: fit then transform. Concrete -- not abstract."""
        return self.fit(X).transform(X)


# This would raise TypeError:
# t = BaseTransformer()  # Can't instantiate abstract class

class StandardScaler(BaseTransformer):
    def __init__(self):
        self.means: list[float] = []
        self.stds: list[float] = []

    def fit(self, X: list[list[float]]) -> "StandardScaler":
        n = len(X)
        num_features = len(X[0])
        self.means = [sum(row[j] for row in X) / n for j in range(num_features)]
        self.stds = [
            (sum((row[j] - self.means[j]) ** 2 for row in X) / n) ** 0.5
            for j in range(num_features)
        ]
        return self

    def transform(self, X: list[list[float]]) -> list[list[float]]:
        return [
            [(row[j] - self.means[j]) / self.stds[j] for j in range(len(row))]
            for row in X
        ]


data = [[1, 100], [2, 200], [3, 300]]
scaler = StandardScaler()
result = scaler.fit_transform(data)
print(result)
# [[-1.2247..., -1.2247...], [0.0, 0.0], [1.2247..., 1.2247...]]
```

## Section 5: Polymorphism and Duck Typing

### Polymorphism

Different objects responding to the same method call in their own way:

```python
class MinMaxScaler(BaseTransformer):
    def __init__(self):
        self.mins: list[float] = []
        self.maxs: list[float] = []

    def fit(self, X):
        num_features = len(X[0])
        self.mins = [min(row[j] for row in X) for j in range(num_features)]
        self.maxs = [max(row[j] for row in X) for j in range(num_features)]
        return self

    def transform(self, X):
        return [
            [
                (row[j] - self.mins[j]) / (self.maxs[j] - self.mins[j])
                for j in range(len(row))
            ]
            for row in X
        ]


def run_pipeline(transformer: BaseTransformer, data):
    """Works with ANY BaseTransformer subclass -- polymorphism in action."""
    result = transformer.fit_transform(data)
    print(f"{type(transformer).__name__}: {result[0]}")

data = [[1, 100], [2, 200], [3, 300]]
run_pipeline(StandardScaler(), data)  # StandardScaler: [-1.224..., -1.224...]
run_pipeline(MinMaxScaler(), data)    # MinMaxScaler: [0.0, 0.0]
```

### Duck typing

Python does not require a formal inheritance relationship. If an object has the right
methods, it works:

```python
class IdentityTransformer:
    """Not a subclass of BaseTransformer, but has the same methods."""

    def fit(self, X):
        return self

    def transform(self, X):
        return X

    def fit_transform(self, X):
        return self.fit(X).transform(X)


run_pipeline(IdentityTransformer(), data)  # Works perfectly
```

> "If it walks like a duck and quacks like a duck, it's a duck."

Duck typing is pervasive in Python. However, abstract base classes add guardrails: they
guarantee that subclasses implement required methods, catching mistakes at class-creation
time rather than at runtime.

## Common Mistakes

1. **Forgetting `super().__init__()`** -- child class silently skips parent initialization,
   leading to missing attributes and confusing `AttributeError`s later.

2. **Wrong MRO assumptions** -- with multiple inheritance, don't assume which parent runs
   first. Print `ClassName.__mro__` to check.

3. **Not implementing all abstract methods** -- Python raises `TypeError` at instantiation
   time, not at import time. If your test file never creates an instance, the bug hides.

4. **Using `isinstance()` too much** -- checking `isinstance(obj, SomeClass)` before
   calling a method defeats the purpose of polymorphism. Just call the method and let duck
   typing work.

5. **Diamond inheritance without `super()`** -- if two parents share a grandparent and
   you hard-code parent calls instead of using `super()`, the grandparent `__init__` runs
   twice.

## Solutions

### Solution: Custom Transformer Hierarchy

```python
import math
from abc import ABC, abstractmethod


class BasePreprocessor(ABC):

    @abstractmethod
    def fit(self, data: list[float]) -> "BasePreprocessor":
        ...

    @abstractmethod
    def transform(self, data: list[float]) -> list[float]:
        ...

    def fit_transform(self, data: list[float]) -> list[float]:
        return self.fit(data).transform(data)


class LogTransformer(BasePreprocessor):

    def fit(self, data: list[float]) -> "LogTransformer":
        return self  # stateless -- nothing to learn

    def transform(self, data: list[float]) -> list[float]:
        return [math.log(x + 1) for x in data]


class ClipTransformer(BasePreprocessor):

    def __init__(self, lower: float, upper: float):
        self.lower = lower
        self.upper = upper

    def fit(self, data: list[float]) -> "ClipTransformer":
        return self  # stateless

    def transform(self, data: list[float]) -> list[float]:
        return [max(self.lower, min(self.upper, x)) for x in data]


def apply_pipeline(transformers: list, data: list[float]) -> list[float]:
    result = data
    for transformer in transformers:
        result = transformer.fit_transform(result)
    return result


# Test
data = [0, 5, 10, 100, 1000, -5]
pipeline = [ClipTransformer(lower=0, upper=500), LogTransformer()]
result = apply_pipeline(pipeline, data)
print([round(v, 4) for v in result])
# [0.0, 1.7918, 2.3979, 4.6151, 6.2186, 0.0]


# Stretch goal: Loggable mixin
class Loggable:
    def fit_transform(self, data: list[float]) -> list[float]:
        print(f"[{type(self).__name__}] Starting fit_transform on {len(data)} items")
        result = super().fit_transform(data)
        print(f"[{type(self).__name__}] Done")
        return result


class LoggableLogTransformer(Loggable, LogTransformer):
    pass


class LoggableClipTransformer(Loggable, ClipTransformer):
    pass


pipeline_verbose = [
    LoggableClipTransformer(lower=0, upper=500),
    LoggableLogTransformer(),
]
result_verbose = apply_pipeline(pipeline_verbose, data)
print([round(v, 4) for v in result_verbose])
# Same output, but with log messages printed
```
