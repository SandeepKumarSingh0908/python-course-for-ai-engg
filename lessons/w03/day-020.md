## Section 1: The Import System

### Module basics

A module is any `.py` file. When you import it, Python runs the file top to bottom and
creates a module object.

```python
# math_utils.py
PI = 3.14159

def relu(x: float) -> float:
    return max(0.0, x)

def sigmoid(x: float) -> float:
    import math
    return 1.0 / (1.0 + math.exp(-x))
```

### Import styles

```python
# Style 1: import the module
import math_utils
print(math_utils.relu(-5))       # 0.0
print(math_utils.PI)             # 3.14159

# Style 2: import specific names
from math_utils import relu, sigmoid
print(relu(-5))                  # 0.0

# Style 3: alias for long names
import math_utils as mu
print(mu.sigmoid(0))             # 0.5

# Style 4: import all (avoid in production code)
from math_utils import *         # imports all public names
```

### What happens during import

1. Python checks `sys.modules` -- if already imported, reuse the cached module
2. Python searches `sys.path` for the module (current dir, stdlib, site-packages)
3. Python executes the module code top-to-bottom
4. A module object is created and cached in `sys.modules`

```python
import sys
print(sys.path[:3])  # current dir, stdlib, site-packages

# Check where a module lives
import json
print(json.__file__)  # e.g., /usr/lib/python3.11/json/__init__.py
```

### The `if __name__ == "__main__"` guard

```python
# data_loader.py
def load_csv(path: str) -> list[dict]:
    """Load CSV file as list of dicts."""
    with open(path) as f:
        headers = f.readline().strip().split(",")
        return [
            dict(zip(headers, line.strip().split(",")))
            for line in f
        ]

# This block runs ONLY when the file is executed directly,
# NOT when it's imported by another module
if __name__ == "__main__":
    data = load_csv("sample.csv")
    print(f"Loaded {len(data)} rows")
```

## Section 2: Packages -- Directories of Modules

A package is a directory containing Python modules and an `__init__.py` file.

### Example project structure

```
ml_project/
    __init__.py           # makes ml_project a package
    config.py             # project configuration
    data/
        __init__.py       # makes data a sub-package
        loader.py         # data loading utilities
        transforms.py     # data transformations
    models/
        __init__.py
        base.py           # base model class
        linear.py         # linear model
        tree.py           # tree-based model
    evaluation/
        __init__.py
        metrics.py        # accuracy, F1, etc.
        plots.py          # visualization helpers
```

### `__init__.py`

This file runs when the package is imported. Use it to expose a clean public API:

```python
# ml_project/__init__.py
"""ML Project: A modular machine learning framework."""

__version__ = "0.1.0"

# Re-export key classes for convenient access
from ml_project.models.linear import LinearModel
from ml_project.models.tree import TreeModel
from ml_project.data.loader import load_csv, load_json

# Now users can do:
# from ml_project import LinearModel, load_csv
```

```python
# ml_project/models/__init__.py
from ml_project.models.base import BaseModel
from ml_project.models.linear import LinearModel
from ml_project.models.tree import TreeModel

__all__ = ["BaseModel", "LinearModel", "TreeModel"]
```

The `__all__` list controls what `from ml_project.models import *` exports.

### Absolute vs relative imports

```python
# Inside ml_project/models/linear.py

# Absolute import -- full path from project root
from ml_project.models.base import BaseModel
from ml_project.data.transforms import normalize

# Relative import -- relative to current package
from .base import BaseModel          # same directory
from ..data.transforms import normalize  # parent's sibling
```

**When to use which:**
- **Absolute imports** are clearer and recommended by PEP 8
- **Relative imports** are useful inside a package when the package name might change

## Section 3: Virtual Environments

### Why virtual environments

Without isolation:
- Project A needs `numpy==1.24` but Project B needs `numpy==1.26`
- Installing a package for one project breaks another
- Deploying to production? Which of the 200 packages on your system are actually needed?

### Creating and using venv

```bash
# Create a virtual environment
python -m venv .venv

# Activate it
# macOS/Linux:
source .venv/bin/activate
# Windows:
.venv\Scripts\activate

# Your prompt changes to show the active environment:
# (.venv) $

# Now pip installs go into .venv/, not the global Python
pip install numpy pandas scikit-learn

# Deactivate when done
deactivate
```

### What venv does

```bash
# Creates this structure:
.venv/
    bin/           # (Scripts/ on Windows) -- python, pip, activate
    lib/
        python3.11/
            site-packages/   # installed packages go here
    pyvenv.cfg    # points to the base Python installation
```

When activated, `.venv/bin` is prepended to `PATH`, so `python` and `pip` resolve to the
virtual environment's copies.

## Section 4: Dependency Management

### requirements.txt

The simplest dependency file:

```
# requirements.txt
numpy>=1.24,<2.0
pandas>=2.0
scikit-learn>=1.3
matplotlib>=3.7
requests>=2.31

# Dev dependencies (often in a separate file)
# requirements-dev.txt
pytest>=7.0
black>=23.0
mypy>=1.0
```

```bash
# Install from requirements
pip install -r requirements.txt

# Generate requirements from current environment
pip freeze > requirements.txt

# Better: use pip freeze only as a snapshot, maintain requirements.txt by hand
# pip freeze includes ALL transitive dependencies which makes the file noisy
```

### pyproject.toml -- the modern standard

```toml
[project]
name = "ml-project"
version = "0.1.0"
description = "A modular ML framework"
requires-python = ">=3.10"
dependencies = [
    "numpy>=1.24",
    "pandas>=2.0",
    "scikit-learn>=1.3",
]

[project.optional-dependencies]
dev = [
    "pytest>=7.0",
    "black>=23.0",
    "mypy>=1.0",
]
gpu = [
    "torch>=2.0",
    "cuda-python>=12.0",
]

[build-system]
requires = ["setuptools>=68.0"]
build-backend = "setuptools.backends._legacy:_Backend"

[project.scripts]
ml-train = "ml_project.cli:main"
```

```bash
# Install the project in editable mode (changes reflect immediately)
pip install -e .

# Install with optional GPU dependencies
pip install -e ".[gpu]"

# Install with dev tools
pip install -e ".[dev]"
```

### Pip essentials

```bash
# Install a package
pip install numpy

# Install a specific version
pip install numpy==1.26.2

# Install with version constraints
pip install "numpy>=1.24,<2.0"

# Upgrade
pip install --upgrade numpy

# Uninstall
pip uninstall numpy

# Show package info
pip show numpy

# List all installed packages
pip list

# Check for outdated packages
pip list --outdated

# Search for import issues
pip check
```

```
    pyproject.toml              # project metadata and dependencies
    README.md
    .gitignore
    src/
        my_ml_project/          # actual package code
            __init__.py
            config.py
            data/
                __init__.py
                dataset.py
                preprocessing.py
            models/
                __init__.py
                classifier.py
                regressor.py
            training/
                __init__.py
                trainer.py
                callbacks.py
            evaluation/
                __init__.py
                metrics.py
            utils/
                __init__.py
                io.py
                logging.py
    tests/
        __init__.py
        test_dataset.py
        test_classifier.py
        test_metrics.py
    notebooks/
        exploration.ipynb
        evaluation.ipynb
    data/                       # not committed to git (in .gitignore)
        raw/
        processed/
    models/                     # saved model artifacts (in .gitignore)
    scripts/
        train.py
        evaluate.py
        serve.py
```

### The `src` layout

Putting code under `src/` prevents a common bug: without `src/`, running tests from the
project root might import from the local directory instead of the installed package,
hiding import errors.

```bash
# With src layout, you must install the package:
pip install -e .

# Then imports always go through the installed package:
from my_ml_project.data.dataset import ImageDataset
```

## Section 6: Publishing (Overview)

### Building a package

```bash
# Install build tools
pip install build

# Build the package
python -m build
# Creates:
#   dist/ml_project-0.1.0.tar.gz   (source distribution)
#   dist/ml_project-0.1.0-py3-none-any.whl  (wheel -- binary distribution)
```

### Publishing to TestPyPI (for testing)

```bash
pip install twine

# Upload to TestPyPI
twine upload --repository testpypi dist/*

# Install from TestPyPI to verify
pip install --index-url https://test.pypi.org/simple/ ml-project
```

### Publishing to PyPI (for real)

```bash
twine upload dist/*
# Now anyone can: pip install ml-project
```

## Common Mistakes

1. **Circular imports** -- module A imports from B, B imports from A. Fix by restructuring
   or moving the import inside a function.

2. **Forgetting `__init__.py`** -- without it (in older Python) the directory is not a
   package. In Python 3.3+, namespace packages work without it, but explicit is better.

3. **Not using virtual environments** -- installing everything globally leads to version
   conflicts and broken environments. Always use `venv`.

4. **`pip freeze` as `requirements.txt`** -- `pip freeze` dumps every transitive
   dependency, making the file fragile and unreadable. Maintain your direct dependencies
   by hand and pin versions for reproducibility.

5. **Relative imports in scripts** -- relative imports (`from .module import x`) only work
   inside packages. Running `python models/linear.py` directly will fail. Use
   `python -m ml_project.models.linear` instead.

6. **Committing `.venv` or `__pycache__`** -- always add these to `.gitignore`.
